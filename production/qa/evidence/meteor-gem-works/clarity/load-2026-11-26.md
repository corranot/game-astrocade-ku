# Meteor Gems: first load, before and after (2026-11-26)

Measured with `node tools/load-time.js prototypes/meteor-gem-works 2`: the page as Astrocade serves it (game.js
bundled inline, gzip), 390x844 phone viewport, 4x CPU slowdown, software GL (SwiftShader), nothing else running.
Times are ms from navigation; two runs each. "Before" is the build on main before this change.

| Profile | Build | Transferred | 3D library ready | First drawn frame |
|---|---|---|---|---|
| slow 4G (150 ms, 1.6 Mbps) | before | 461 kB | 2723 / 2739 | 9312 / 8593 |
| slow 4G | after | 281 kB | 1631 / 1643 | 5360 / 5060 |
| 4G (60 ms, 9 Mbps) | before | 461 kB | 692 / 695 | 6723 / 6514 |
| 4G | after | 281 kB | 369 / 373 | 3639 / 3634 |

The warm sky with the glowing meteor (`load-splash.jpg`) shows as soon as the HTML arrives, before the 3D library.

## Root causes found
- `three.module.min.js` on cdnjs imports `./three.core.js`, the **unminified** 1.47 MB core (211 kB brotli),
  not `three.core.min.js`. The import map now maps that URL to the minified core (391 KB, 84 kB brotli), and both
  library files are `modulepreload`ed so they download in parallel instead of one after the other.
- The first frame compiled all 33 shader programs synchronously. `prewarm()` now uses `compileAsync` (parallel
  compile where the driver supports it) and the loop starts when it resolves, or after `quality.warmMs` at most.

## Not proven
- Real phone numbers. SwiftShader compiles shaders on the CPU, so the last step (about 1.5 s here) is much
  shorter on a phone GPU. Scene building is about 1.7 s at 4x CPU slowdown and is the next thing to cut.
- Other games in this repo use the same import map and still download the unminified core.
